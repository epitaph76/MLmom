# Устойчивый запуск через реальную LLM

Исходные причины сбоев и неизменяемые диагностические материалы описаны в
[REAL_API_DIAGNOSTICS.md](REAL_API_DIAGNOSTICS.md). Новые проверки не заменяют
старые логи и не используют mock LLM вместо организаторской Qwen.

## Изменения

- Исходящие сообщения проходят allowlist Chat Completions. Ответы провайдера,
  включая reasoning и расширения, остаются в очищенной от секретов трассе.
  Клиент не передаёт лимиты выходных токенов.
- Первый раунд использует `execution_mode=adapter_only`: LLM возвращает короткую
  обёртку `LibraryCandidate` / `load_adapter`, AST-проверка запрещает иной код.
  Признаки обрабатывает существующий адаптер. Сложные кандидаты доступны после
  готового submission и при достаточном бюджете.
- История последних экспериментов приходит в payload. При пустой истории
  `read_history` не предлагается. Повтор одинакового read-only результата
  прекращает tool loop одним финальным запросом JSON без инструментов.
- Окна ролей сохраняются в SQLite: анализ задачи 180 с, гипотезы 90 с,
  планер гипотезы 180 с, валидатор 90 с. Повторы, repair и resume используют
  исходный deadline. Последние 60 с полного окна кодера в 300 с резервируются
  для записи и smoke; у коротких тестовых окон резерв пропорционально меньше.
- Ошибка формата валидатора получает одну попытку исправления неизменного плана.
  Содержательное отклонение может вернуть планеру замечания. HTTP 500/502/503/504
  повторяются не более двух раз, с задержками 1 и 2 с в пределах дедлайна.
- Реальный повтор выявил timeout семантического валидатора на 90 с. Его контекст
  сокращён до задачи, признаков, одного плана и относящихся к проверке инструкций.
  При исчерпании временных сетевых повторов только `adapter_only` может пройти
  по детерминированным проверкам с явным `planning.validation_degraded` и
  предупреждением в summary. Обязательный LLM-кодер, точная AST-проверка, smoke,
  проверка признаков и реальная оценка остаются обязательными. Этот путь не
  применяется к содержательным отклонениям, ошибкам JSON, квоте или custom-коду.
- Параметры CPU в model_params, точно совпадающие с CPU плана, удаляются как
  избыточные: ресурсами по-прежнему управляет оркестратор. Иные значения
  отклоняются обычной проверкой.
- `based_on` указывает только на проверенный candidate_id;
  `based_on_hypothesis_id` хранит происхождение гипотезы. Обязательные исключения
  target/ID добавляются до валидации без отдельного обращения к LLM.

## Сохранение

Внутри каталога запуска сохраняются `source_revisions/`, `candidates/`,
`plans/`, `splits/`, `runs/`, `predictions/`, `submissions/` и полная трасса.
Каждая публикация CSV имеет отдельную копию и JSON со ссылками на модель,
исходник, план и выбранные параметры. `artifact_index.json` содержит размеры
и SHA256 файлов. `run.completed` означает наличие submission; отсутствие
результата сопровождается `run.failed` и причинами в `summary.json`.

## Реальные локальные проверки

```powershell
.\.venv\Scripts\python.exe scripts/run_real_diagnostics.py --output artifacts/repaired-real-20261021
```

Скрипт использует два исходных ZIP из Downloads, распаковывает отдельные копии
и последовательно запускает обе задачи. На задачу отводится суммарно 1800 с,
включая повторные попытки: до 1740 с самому pipeline, оставшееся время —
независимой проверке сохранённой модели. Worker использует 2 CPU и не более
3 ГБ суммарной RAM; одновременно работает один worker. Финальный резерв 300 с,
не более двух раундов, timeout запроса до 300 с.

Скрипт сохраняет исходный runtime ZIP, хеши входов и исходников, конфигурацию,
stdout/stderr, наблюдения RSS каждые 5 с, итоговый отчёт и индекс артефактов.
Повтор `--case regression` или `--case multiclass` в том же каталоге учитывает
время предыдущих попыток в `budget.json`.

После успешного запуска отдельный worker загружает финальную модель и повторяет
предсказания первых 128 строк test. Проверяются совпадение с сохранённым CSV,
полное число строк, столбцы, порядок ID, отсутствие пропусков/бесконечностей и
допустимые классы. Верификация находится в `verification/report.json`.

Локальные holdout-метрики не являются платформенным score.

## Актуальный профиль циклов улучшения

Описанный выше профиль 1800 секунд / 2 CPU / 3 ГБ относится к предыдущим отчётам. Текущий `run_real_diagnostics.py` использует согласованный профиль трёх циклов: общий час на задачу (включая повторные попытки и проверку), 4 CPU / 4 ГБ workers, один worker, три раунда, пакетный Optuna внутри гипотезы. Финальный резерв pipeline — 600 секунд; независимая проверка получает до 45 секунд из отдельного 60-секундного окна в пределах общего часа. Подробности и поля приёмки: [IMPROVEMENT_CYCLES.md](IMPROVEMENT_CYCLES.md).
