# Длительности как информация и атомарная замена признаков — runtime v5

В прежнем прогоне ансамбли mean/weighted не дошли до обучения из-за
`insufficient_complete_recipe_budget`. Контроллер складывал wall time исходных
экспериментов, включая целую Optuna-study, и сравнивал сумму с лимитом рецепта.
Это разные виды измерений: время поиска не является временем одного refit.
Длительности независимых заданий также не определяют суммарное время при параллельном
исполнении. Исходные результаты и архивы v3/v4 сохранены.

В v5 исторические длительности используются как информация для агентов. Удалены
отказы planning/coding/ensemble по прогнозу цены полного эксперимента, сумма исходных
длительностей и множитель 4 для weighted/stack. Отсутствуют вычисленные по таким
оценкам окна группы, отсечение альтернатив ради предполагаемых будущих циклов и
вычитание всего запрошенного fit-limit перед генерацией кода. План с длинным лимитом
может стартовать в меньшем фактическом остатке времени; исполнитель ограничит его
реальным оставшимся окном, действующим лимитом этапа и общей конфигурацией.

Сохраняются явно включённые таймауты, общий дедлайн, выделенный final reserve,
пользовательские лимиты trials, остановка и единый учёт CPU/RAM. План больше не
отклоняется программно за несовпадение оценочной длительности с остатком времени.
Plan validator по-прежнему оценивает содержательную корректность эксперимента.
`target_completed_rounds` остаётся целью количества циклов, а не основанием
искусственно делить время и отклонять уже выбранные агентом эксперименты.

Независимые кандидаты и рецепты допускаются общим scheduler параллельно, когда
хватает ресурсов. Внутри текущего SDK FrozenEnsemble компоненты одного рецепта
обучаются последовательно. Эта правка не меняет внутреннюю параллельность SDK и
не обещает, что любой рецепт уложится в дедлайн. В обоих случаях сумма прошлых
HPO-экспериментов не используется для отказа до измерения.

## Замена признаков

`FeatureProposal.action` принимает `add`, `remove`, `replace`, `stop`.
Для `replace` указываются обе стороны: имена удаляемых признаков в `remove` и
новые определения в `features`. Ответ старого формата `action=add` с обеими
сторонами однозначно читается как `replace`.

Например, при 16 активных признаках можно удалить `old_ratio` и добавить
`state_mean_year`. Runtime сначала строит итоговый набор, затем проверяет его
имена/DSL/доступные колонки и лимит 16. Единственный эксперимент сравнивает
итоговый набор с текущим принятым набором при одинаковой модели, параметрах,
folds и seed. Промежуточный набор из 15 признаков не обучается и не должен
самостоятельно улучшать метрику.

Замена расходует одну конфигурацию. Обе стороны, родитель, результат и ссылки
на измерения сохраняются в pending/evidence. Planner видит исходный и итоговый
наборы и полное предложение. Resume завершает зарезервированный эксперимент,
используя сохранённый результат без повторного предложения или fit. Если итоговая
замена не улучшилась, контроль сохраняется. Неизвестное имя удаления возвращается
агенту с конкретным списком отсутствующих имён.

## Проверки и выпуск

Регрессии находятся в `tests/test_advisory_costs_and_replacement.py`: фактическое
обучение mean/weighted при огромных исторических длительностях источников,
кодирование в небольшом фактическом остатке, атомарная замена при 16 признаках,
старый формат ответа, отказ по измеренному результату, конкретная ошибка удаления
и resume без повторного обучения. Существующие проверки истёкшего дедлайна,
ресурсов, остановки и сохранения CSV остаются в suite.

Новый runtime contract: 5. Использовать новый каталог запуска; активное состояние
v3/v4 не переносить. Формат inference-моделей SDK остаётся прежним.
Новый архив: `dist/mlmom-advisory-costs-replacement-v5.zip`.
Итоговые отчёты: `artifacts/advisory-costs-replacement-v5-verified/`.
Проверки выполняются без платных API-запросов.

Результат проверки 25.10.2026:

- Полный suite в Docker mlmom-ml:test: 365 тестов, 0 failures/errors/skips,
  757 секунд; 8 CPU / 6 GiB, сеть отключена. `tests.json` и `tests.log` в каталоге проверки.
- 27 проверок из распакованной сборки, включая реальное обучение mean/weighted
  с завышенной исторической стоимостью источников и atomic replacement/resume, прошли.
- Все пять сохранённых add+remove ответов исходного прогона прочитаны как replace:
  итоговые наборы сохраняют 16 признаков. Это проверка исправления контракта,
  а не заявление об улучшении метрик этих предложений. См. `recorded_replacement_replay.json`.
- При отдельном исполнении примера REFERENCE выявлено пропущенное обязательное
  rationale; оно добавлено. После этого финальный ZIP прошёл ещё 10 проверок
  skills/упаковки. Пример исполнен на Pydantic 2.10.6 / NumPy 1.26.4 / Polars 1.26.0.
- Исполняемые Python-файлы полного suite, исходников и финального ZIP идентичны.
  Единственное изменение после снимка полного suite — rationale в примере
  `skills/shared/candidate_sdk/REFERENCE.md`; разница сохранена в `final-reference-delta.json`.
