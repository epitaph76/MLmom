# Реальные прогоны Qwen — 21 октября 2026

Оба отдельных запуска текущего кода завершились с `no_successful_candidates`: модели не дошли до обучения, итоговые CSV не созданы. Это проверка реального API, в отличие от предыдущих успешных smoke с mock LLM.

Организаторы сообщили, что первая загрузка, до логирования и последующих изменений, также завершилась с `no_successful_candidates` и без файлов предсказаний на обеих задачах. Это устанавливает конечную причину тех нулевых баллов, но не позволяет восстановить внутренние ошибки старой версии. Ниже — доказательства для текущей версии.

## Условия и результаты

Runtime соответствует bundle `a95caadc047c4d1d72814caf9c45285af2b1c8bbdaafe568b455171e88643368`; в ходе прогонов исходники не менялись. Модель: `qwen/qwen3.8-27b`, подключение организаторов. Архивы распакованы в отдельные каталоги внутри artifacts; исходные Downloads не изменялись.

Локальный профиль: до 30 минут на задачу, резерв 5 минут, максимум два раунда, 2 CPU, 3 ГБ суммарной памяти workers, один worker одновременно, общий лимит кодирования до 300 секунд. API timeout регрессии был сокращён до 180 секунд; классификация использовала штатные 300 секунд. Поэтому влияние таймаутов регрессии нельзя напрямую переносить на штатный профиль. Трёхчасового прогона не было.

Во время этих запусков не было OOM, остановки по памяти или вызовов worker с `action=train`. `/models` ответил за 0,406 секунды: доступность gateway подтверждена, работоспособность backend генерации этим не доказывается. Причины ожидания конкретного запроса без ответа — очередь, вычисления модели или другая серверная проблема — клиентская трасса не различает.

## Подтверждённые проблемы

1. **Кодер не создаёт первый файл.** В регрессии обе попытки закончились `Missing candidate.py` и `APITimeoutError`. Первый кандидат получил 300 секунд, а второй — лишь 18,26 секунды: остальной исследовательский бюджет уже израсходован на LLM и защищённые окна обучения/предсказания. В классификации первая версия упёрлась в `max_tokens=12000`, следующая — в timeout. Ни одного Python-файла кандидата не сохранилось.
2. **Планер повторяет запросы без новых данных.** В регрессии seq 89–169: девять одинаковых `read_history(kind="evaluation", limit=5)`, каждый вернул `status=ok, data=[]`. Следующие requests содержат правильный `tool_call_id` и точный ToolResult — ошибка доставки исключена. Первый baseline-план потребовал 11 ответов и 339 875 total tokens. Восемь лишних повторов заняли 27,594 секунды; лимит `max_steps` ограничивает длину цикла, но не распознаёт отсутствие прогресса.
3. **Поля ответа пересылаются как история запроса.** `RoleClient` добавляет полный `message.model_dump()`: вместе с допустимыми полями уходят `reasoning_content`, `provider_specific_fields` и `tool_calls[].index`. В request seq 178 очистка до стандартных полей уменьшает JSON с 217 537 до 75 820 символов. Это измерение размера; сокращение billable tokens на тот же процент и причинность tool loop не доказаны.
4. **Валидатор тратит ответ на reasoning и запускает перепланирование.** В регрессии seq 195: `completion_tokens=12000`, `finish_reason=length`, `content=null`; далее повторяется планирование уже существующего baseline. В классификации seq 244 точно такой же пустой ответ получил сам кодер. Другой ответ валидатора классификации не содержал корректный JSON. Часть времени уходит на восстановление формата, а не на улучшение моделей.
5. **Ссылки гипотез и кандидатов смешаны.** Альтернатива регрессии ссылается на `lgbm_baseline` как ID гипотезы, а проверка требует ID версии кандидата. После неудачи baseline готовой версии нет. Перепланирование исправило ссылку на `null`, затратив дополнительные API-вызовы.
6. **Служебные ограничения требуют лишнего LLM repair.** На обеих задачах постановщик сначала не включил target в `excluded_feature_columns`, затем исправил ответ. При этом Python и так исключает target и ID при построении признаков. Эти безопасные обязательные исключения можно дополнять детерминированно.
7. **Временная серверная ошибка обрывает альтернативу.** Последний запрос планера классификации завершился HTTP 502 (`upstream error`, seq 447–449). Для этого класса ошибок сейчас нет ограниченного HTTP retry. Альтернативный CatBoost-план не был принят.

Гипотезы классификации также требуют внутреннего duplicate-aware k-fold, хотя старт должен быть простым. Флаг `strategy=single` ограничивает HPO, но сам по себе не ограничивает сложность произвольного кода и текста гипотезы. Фактического выполнения k-fold в этих запусках не было.

## Приоритет следующих изменений

- Нормализовать исходящую историю до полей Chat Completions; полные provider responses оставить в trace.
- Убрать чтение пустой истории в первом раунде и прекращать одинаковые read-only tool loops ограниченным запросом финального JSON.
- Сохранить обязательного LLM-кодера, но первый план ограничить коротким кандидатом на существующем адаптере, без самописного CV и нового preprocessing. Сначала добиваться одного проверенного файла, затем добавлять сложность.
- Разделить бюджеты Planner, Validator и Coder; восстанавливать ответ валидатора без повторного планирования. Оставлять кодеру окно на запись и smoke, учитывать остаток перед запуском новой гипотезы. Политику reasoning менять только после проверки поддержки провайдером.
- Разделить зависимости гипотез и ссылки на готовые версии; дополнять обязательные исключения в Python; добавить ограниченные retries для временных 5xx.
- Добавить mock-последовательности именно этих ответов: повтор пустой истории, response-only поля, `length+null`, отсутствие файла после timeout, неверный `based_on`, временный 502. Прежние 81 тест подтверждали другие сценарии и не воспроизводили это поведение реальной модели.

Эти изменения в диагностических прогонах не применялись. Итоговый платформенный score и качество моделей оценить нельзя: предсказаний нет.

## Артефакты

Все материалы: `artifacts/real-diagnostics-20261021-d893fe/`.

- `reports.json` — exit codes, длительности, память и результаты обеих задач.
- `manifest.json`, `config-regression.json`, `config-multiclass.json` — входы и точные настройки.
- `resources.jsonl` — наблюдения памяти каждые пять секунд.
- `regression/trace.md`, `multiclass/trace.md` — отчёты с полными payloads по ссылкам; рядом SQLite и JSONL.
- `regression/candidates/`, `multiclass/candidates/` — не прошедшие проверку версии и причины отказов.
- `connectivity/trace.md` — отдельная проверка доступности `/models`.

Последнее событие `run.completed` обозначает завершение исполнения графа и может содержать `status=failed`; итог нужно проверять по payload и `summary.json`. Это название события также стоит уточнить.
