# MLmom

## Назначение
MLmom — единый агент для табличных ML-задач: от анализа условия и данных до обучения, сравнения моделей и готового `submission.csv`. Весь жизненный цикл запускается одной командой и управляется LangGraph 0.6.7.

## Запуск на платформе
Платформа предоставляет Python 3.12, зависимости и переменные `OPENAI_API_KEY`/`OPENAI_BASE_URL`; `OPENAI_MODEL` необязателен и по умолчанию равен `qwen/qwen3.8-27b`. Пути данных разрешаются относительно `task.md`, итоговый файл записывается рядом с ним.

```bash
python solution.py task.md
```

## Локальный запуск
Установите зависимости заранее и сохраните ключ в игнорируемом `.env`; dev-профиль читает `OPENAI_*` и совместим со старыми `ROUTERAI_*`. Платформенный профиль читает подключение только из окружения.

```bash
python -m pip install -e .
python solution.py /path/to/task.md --profile dev
```

## Ключ организаторов
Локальные настройки: `OPENAI_BASE_URL=https://changellenge.up.railway.app/v1` и `OPENAI_MODEL=qwen/qwen3.8-27b`; реальный ключ хранится только вне Git. Командный лимит составляет 600 рублей в день со сбросом в 03:00 МСК.

## Бюджет
Один запуск обрабатывает одну задачу за 180 минут, из которых минимум 40 резервируются для финального обучения. Генератор предлагает не более двух новых гипотез за раунд. Первый раунд использует `adapter_only`: обязательный LLM-кодер создаёт короткую обёртку над готовым адаптером, AST-проверка запрещает custom-код и собственный CV. Baseline обучается и публикуется перед подготовкой альтернативы. На код, исправления и проверки одной гипотезы отводится общий лимит до 300 секунд; последние 60 секунд полного окна резервируются для записи и smoke. Repair и resume не обновляют дедлайны.

Сложные планы доступны со второго раунда после корректного submission и при достаточном бюджете. Тяжёлые библиотеки проверяются по запросу выбранного плана; все worker-запуски, включая smoke, probe и predict, используют общий admission CPU/RAM и максимум три свободных слота. Тесты используют короткие профили, а цель первого submission — 10 минут, без гарантии при медленном API.

У LLM-ролей есть отдельные сохраняемые окна: описание задачи 180 секунд, гипотезы 90, планер 180, валидатор 90. Перед началом новой гипотезы проверяется бюджет всего пути до предсказаний. Старый короткий `profiles/dev.json` может быть недостаточен для реального API с этими окнами; для двух локальных часовых проверок с тремя циклами используйте `scripts/run_real_diagnostics.py`. Условия, резервная проверка строгого адаптера при сетевом сбое валидатора и сохранение артефактов описаны в [RELIABLE_REAL_RUNS.md](docs/RELIABLE_REAL_RUNS.md).

## Тесты и ZIP
Обычные тесты используют mock LLM, а обращения к реальному API выполняются отдельно. Сборщик создаёт плоский ZIP с `solution.py`, `requirements.txt` и `mlmom_bundle.py`, поскольку Boosters не переносит вложенные папки.
Проверенный [архив для загрузки](submission/mlmom-solution.zip) и [отчёт проверки](VALIDATION.md) включены в репозиторий.

```bash
python -m unittest discover -v
python scripts/package_solution.py --output dist/mlmom-solution.zip
```

## Восстановление
Укажите постоянный `--run-dir`, а после прерывания запустите ту же команду с `--resume`. Входные файлы и конфигурация должны совпадать; исходный дедлайн сохраняется.

```bash
python solution.py task.md --run-dir artifacts/task-run
python solution.py task.md --run-dir artifacts/task-run --resume
```

## Ограничения
Forecasting распознаётся, но исполнение отложено; clustering требует числового пространства оценки, anomaly detection — явных evaluation labels. Процессная изоляция ограничивает ресурсы и последствия ошибок. Отдельный audit не используется: внешний holdout меняется между циклами (seed 42, 43, 44, ...). Чемпион с сохранёнными кодом и параметрами переобучается на train текущего цикла и сравнивается с новыми кандидатами только на общем holdout этого цикла.

## Циклы улучшения и HPO

Гипотеза включает кодирование, проверки, обучение и Optuna внутри одного большого цикла. Сначала публикуется быстрый baseline CSV, затем подбираются параметры той же реализации. Одна study сохраняется на диске; пакеты по 5 trials продолжаются при относительном приросте внутренней метрики не менее 0,5%, максимум 15 trials / 600 секунд. Любой лучший результат сохраняется. При плато планер получает диагностику и предлагает изменение логики или preprocessing. Native AutoML не оборачивается в Optuna.

LightGBM использует native categories; LightGBM/CatBoost поддерживают внутреннюю validation и early stopping для доступных целевых метрик. sklearn `estimator=linear` использует sparse word/character TF-IDF для текста, LogisticRegression для классификации и Ridge для регрессии. Все преобразования обучаются внутри допустимого split.

Профиль `scripts/run_real_diagnostics.py`: 3600 секунд на задачу, 600 секунд финального резерва плюс минута независимой проверки, максимум три цикла, 4 CPU / 4 ГБ workers, один worker, задачи последовательно. Общий час включает проверку и повторные попытки. `process_acceptance` отдельно показывает завершённые циклы и Optuna trials; корректный CSV сам по себе не означает выполнение цели теста.

Подробнее: [реализация и проверки](docs/IMPROVEMENT_CYCLES.md).

Планирование использует компактный контекст без повторных полных историй. Генератор гипотез, планер и валидатор имеют окна по 210 секунд в пределах общего дедлайна. Первый ответ — итоговый JSON; дополнительные чтения требуют явной причины и ограничены двумя запросами. Повтор планирования остаётся в текущем цикле, полученные гипотезы и планы сохраняются. Подробности: [IMPROVEMENT_CYCLES.md](docs/IMPROVEMENT_CYCLES.md).
